## 2. Guide gaps — host source read instead of the guide

**54 of 120 completed tool calls (45%) read host source under `~/repos/t3code-extensible`.**

The guide was found and read first: at 14:20:19 the builder called `ListMcpResourcesTool`, then
read `t3code://extensions/guide`, `…/scaffold` and `…/installed` in the next seven seconds. The
`instructions` string and the three resources did exactly their job. **Nineteen seconds later,
at 14:20:45, it opened the fork checkout and largely stayed there.**

**One theme accounts for most of it.** The guide documents the seam — the protocol, the
manifest, the host web API — and assumes the client API is already known. But an extension of
any substance is mostly _client API calls_; the seam is the small part. A builder that has read
the whole guide still does not know how to create a thread. Fixing this does **not** mean
documenting the client API in the extension guide: it means the guide saying, in one paragraph,
that the extension is an ordinary client, that `packages/contracts/src/orchestration.ts` is the
reference for what it can dispatch, and that the reference extension shows a call. That stays
general, which §14 requires.

### The isolation caveat, which is mine

**The run was not clean-room in the sense §14 intended**, and the runbook is why. It isolated
the working folder and the T3 home but left `~/repos/t3code-extensible` readable, and the
builder went straight there. So the 54 reads are an _upper_ bound on real guide gaps: some are
a builder taking the shortest path to certainty rather than a guide that failed. The clustering
above is still the right signal — it says which questions it had — but "45% of calls" should
not be quoted as a guide-quality score. **A re-run must deny read access to the fork checkout**;
see §7.

## 6. The shape the extension took

It built a single Node process that speaks the wire protocol directly, with a hand-written RPC
client — the same conclusion the in-tree reference extension reached independently, which is
evidence the protocol's shape is legible rather than that the reference is being copied. Its
own SQLite lives under `T3_EXT_DATA_DIR` with `AUTOINCREMENT` ids, and the restart test shows
the durability requirements were understood rather than approximated.

Two decisions worth noting. It polls the dashboard at 1.5s rather than subscribing — the
simpler of the two the spec allows, and it did not go looking for a change stream. And it wrote
`test/fakeHost.mjs`, a fake host speaking the real protocol, and ran the spec's §7 against it,
reporting 18/18. **That fake found a real bug before the run did**: a message arriving inside
the wake cooldown for an idle agent would have sat undelivered, and it added a retry pass. An
extension author independently building a protocol-level test double says the protocol is small
and well-specified enough to fake — the strongest evidence in this run that the wire contract is
right.

## 7. What changes

1. **Add an install path from the UI.** Settings → Extensions → "Add extension folder",
   appending the settings entry and starting it. The single highest-value fix; without it the
   design's "Deploy is a human click" story has no first step.
2. **One paragraph in the guide** saying an extension is an ordinary client, pointing at
   `packages/contracts/src/orchestration.ts`, and pointing at the reference extension's
   dispatch call. General, not spec-shaped.
3. **State the token's scopes** in the guide — currently "plus orchestration scopes".
4. **A re-run must deny the fork checkout.** The runbook isolated the working folder and the
   home but not read access to `~/repos/t3code-extensible`. Until that is closed, the
   host-source count measures convenience as much as it measures the guide.
5. **Fix the checklist script's timing** — done: a ≥60s busy prompt, and an explicit note that
   a woken agent drains inside its own turn, so the evidence is the wake turn's content and not
   a later `inbox` call.
6. Investigate the `pnpm` failure before the next uptake.

**Deliberately not doing:** documenting `spawn_agent`, message queues, or anything else this
spec needed. Every one of those would tune the guide toward this test and prove nothing about
the next extension (§14).
