# End-to-end: the server seams with the reference extension (2026-09-06)

A live run of the whole server-side seam against the built reference extension,
on `3da9548eb` plus the fixes below. One dev server in a worktree with its own
`.t3`, one real Claude Code thread, no browser: everything here was driven over
the ordinary client protocol and HTTP.

**All nine items pass.** Two needed a fix first; both are recorded under
[Fixes](#fixes), and one design gap that nothing in the run depended on is
recorded under [Open](#open).

Setup: `serverPort=15533 webPort=7493 baseDir=<worktree>/.t3`, extension
registered through a settings entry (`extensions: [{ name, path, enabled }]`)
pointing at `extensions/reference/dist`.

### 1. Spawn and handshake

The extension's own captured stdout, read back through `extensions.admin.logs`:

```
[reference] connected to host 0.0.38 (protocol v1), environment 4cf3d105-…, data at <home>/userdata/extensions/reference
[reference] HTTP prefix "reference" served at /ext-api/4cf3d105-…/reference
[reference] ready (connection 08dd01cc-a987-474e-9760-8185eeb4fa0f)
```

`ready` is printed from the `attached` event, so it is proof that
`extensions.connect` opened — the readiness signal. The server's trace log
carries `ws.rpc.extensions.hello`, `.registerTools`, `.registerHttpPrefix`,
`.registerWebEntry`, `.setBadge` and, under its own name because it is a
stream rather than a request, `ExtensionRegistry.connect`.

> Note for anyone repeating this: `extensions.connect` does **not** appear as
> `ws.rpc.extensions.connect`. Grepping for that pattern and finding nothing is
> not evidence that the stream failed to open.

### 4. HTTP proxy

```

{"name":"reference","startedAt":"…","environmentId":"4cf3d105-…","echoCount":0,"lastEcho":null}
```

Negatives, all as intended: no token → **401**, bad token → **401**, unknown

## Fixes

### 1. Deploy and enable were interrupted by the caller's scope

`ExtensionSupervisor.start` forked the supervisor fiber with
`Effect.forkScoped`, which attaches it to whatever scope is ambient. At startup
that is the layer's scope and everything works. But `ws.ts` calls both
`deploy` and `setEnabled` inside `Effect.scoped(...)`, so over RPC the new fiber
was attached to the **request's** scope and interrupted the moment the call
returned.

The visible symptom: `extensions.admin.deploy` left the extension `stopped` with
no error and `restartCount: 0`, and its folder hash was never re-read — because
the re-read happens inside the fiber that had just been killed. `setEnabled
true` was broken the same way. Both are the only ways a user starts an extension
after boot, so this made the Settings screen's two main actions dead.

The fix captures the layer's own scope in `make` and forks into it:

```ts
const supervisorScope = yield* Effect.scope;
…
const fiber = yield* Effect.forkIn(supervise(source.name, source), supervisorScope);
```

The existing deploy test could not catch this: it built the supervisor and
called `deploy` inside one shared `Effect.scoped`, so there was no separate
caller scope to close. The added regression test reproduces the RPC shape —
supervisor in an outer scope, `deploy` in an inner one that closes — and was
confirmed to fail before the fix and pass after.

### 2. Two misleading strings

- `t3 pair --extension` printed `node dist/server.js` as the command to run.
  The manifest names the entry, and the reference's is `server.mjs`, so anyone
  copying the block landed on a file that does not exist. It now points at the
  manifest field rather than guessing a filename.
- The reference extension logged the data directory from the hello ack rather
  than the one it actually writes to. Identical when supervised, different in
  dev mode — where the operator chose the directory, which is the one worth
  printing.

## Open

**`changed` is unreachable while an extension runs.** The folder hash is only
read in `ExtensionSupervisor.supervise` (at start) and in `deploy`. Nothing
re-reads it while the process is up, so `folderHash` can never drift from
`runningHash` on its own and `changed` never becomes `true` — the Deploy
affordance design §6.3 describes ("when the folder's hash differs, the extension
is marked changed") cannot light up. Deploy itself works; it is the _prompt_ to
deploy that is missing.

Not fixed here because the choice is a design one: re-hash on
`extensions.admin.list` (on demand, no background I/O, correct exactly when
Settings or the nav renders) versus a periodic poll (continuous hashing of every
extension folder, which sits badly with the repo's performance rules). The
former looks right, and it needs the registry to be able to read a folder, which
today only the supervisor can.
