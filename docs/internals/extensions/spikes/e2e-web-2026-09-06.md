# End-to-end: the reference extension's web surface

Verification run for the web half of the seam, on 2026-09-06 against
`9b1914a7e` plus the fix below, macOS 15 (darwin 25.5.0, arm64), Node 24.19.0.
Everything here was proved without a browser; the browser pass is a separate
note.

**One real defect found and fixed** (see "The minted URL did not resolve"). The
rest of the surface behaved as designed.

## How it was run

The reference extension is standalone, so it installs and builds on its own:

```bash
cd extensions/reference && npm install && npm run build   # → dist/
```

The host is the ordinary server with a launch flag, on its own home:

```bash
node apps/server/src/bin.ts serve \
  --base-dir "$PWD/.t3" --port 13901 --no-browser \
  --extension "reference=$PWD/extensions/reference/dist"
```

`serve` prints a pairing token; `node apps/server/src/bin.ts pair --base-dir
"$PWD/.t3"` mints another, because a pairing token is one-time and a second run
of a probe needs its own.

The probe is a throwaway Node script that walks the browser's own path —
`POST /api/auth/browser-session` with the pairing token, then `POST
/api/auth/websocket-ticket`, then `ws://…/ws?wsTicket=…` speaking the five JSON
RPC frames. Two things about that are worth writing down because both cost time:
the ticket query parameter is **`wsTicket`**, not `ticket`, and the pairing
token is spent by the first `browser-session` call.

## What the host reported

`extensions.admin.list` and the first frame of `extensions.admin.subscribe` are
identical, which is the intended contract — a subscriber never has to `list`
first:

```jsonc
{
  "name": "reference",
  "source": "launch-flag",
  "enabled": true,
  "state": "running",
  "version": "1.0.0",
  "protocolVersion": 1,
  "folderHash": "3dd91d90…",
  "runningHash": "3dd91d90…",
  "changed": false,
  "tools": ["reference_echo"],
  "rejections": [],
  "httpPrefix": "reference",
  "web": { "entry": "web/entry.js", "css": "web/entry.css", "label": "Reference" },
  "restartCount": 0,
}
```

So the whole registration path works end to end from a launch flag: the process
was spawned, said hello, registered a tool, an HTTP prefix and a web entry, and
the host hashed its folder.

## The minted URL did not resolve

`extensions.admin.assetUrls` returned a well-formed signed URL that **404'd**,
and so did the stylesheet. Nothing in the extension is at fault, and the client
loader is correct: the two halves of the asset route disagreed about what a path
in the URL is relative to.

- The manifest states `web.entry` relative to the **extension folder**
  (`web/entry.js`), and `mintExtensionAssetUrls` put that string in the URL
  verbatim.
- `resolveWebAssetPath` resolves the requested path against the **web entry's
  own directory** (`<folder>/web`).

So `<folder>/web` + `web/entry.js` = `<folder>/web/web/entry.js`, which does not
exist. Both halves passed their own tests: the route's test hand-built the path
as `entry.js`, which is the convention the route wants, and nothing served a URL
that minting had produced.

**The route's convention is the right one**, and the fix belongs in minting.
A code-split bundle's `import('./chunk.js')` is resolved by the browser against
the entry's URL, so the entry has to sit at the root of the extension's asset
space for a sibling chunk to land beside it on disk. With the paths as they were
minted, chunked builds would have failed the same way.

Fixed in `mintExtensionAssetUrls` by stripping the web entry's directory prefix,
with `webAssetDirectory` widened to `Pick<ExtensionWebEntry, "entry">` so the one
definition serves both sides. Two tests in `ExtensionHttpRoutes.test.ts` close
the seam — one serves the URLs `assetUrls` actually minted, one resolves a
sibling chunk relative to the minted entry. Both fail without the fix.

The general lesson, worth applying beyond this route: **a test that hand-builds
the input a producer is supposed to generate does not test the producer.**
Anything that mints a URL should be checked by serving what it minted.

## The asset route, after the fix

| Request                                                         | Result                                               |
| --------------------------------------------------------------- | ---------------------------------------------------- |
| `GET <entry>` with no cookie and no header                      | **200**, `text/javascript; charset=utf-8`, 196,589 B |
| `GET <css>`                                                     | **200**, `text/css; charset=utf-8`, 1,100 B          |
| Forged token (`AAAA.BBBB`)                                      | 404                                                  |
| Correct payload, last two signature characters changed          | 404                                                  |
| Correct token, a different extension name in the path           | 404                                                  |
| `..%2F..%2Fextension.json`                                      | 404                                                  |
| Hand-minted token with a **past** `expiresAt`, correctly signed | 404                                                  |

The last row is the one worth having: the probe read
`userdata/secrets/extension-asset-signing-key.bin` and signed its own claims, so
a hand-minted token with a _future_ expiry served **200** as a control. That
makes the expired 404 a clock check rather than a signature failure — the two are
indistinguishable from the outside, which is the point of answering both with 404.

Serving the bundle needs **no session at all**, which is what makes a same-origin
`import()` possible: `import()` cannot set an `Authorization` header. The
response carries `cache-control: private, max-age=3600` and
`x-content-type-options: nosniff`.

The served bundle contains no `eval(`, which the desktop CSP would block, and the
stylesheet is scoped — every rule starts `.t3ref-`, and it reads host theme
variables (`var(--color-foreground, #262626)`) rather than setting them.

## The proxied HTTP surface

The mounted UI reaches its own process through `hostApi.fetch`, which is
`/ext-api/<environmentId>/<prefix>/<path>` under the host's ordinary auth:

| Request                                              | Result                                                       |
| ---------------------------------------------------- | ------------------------------------------------------------ |
| `GET /ext-api/<env>/reference/status` with a session | **200**, `application/json`, the extension's own status body |
| Same path, a foreign environment id                  | 404                                                          |
| Same path, no session                                | 401                                                          |

The 404 for a foreign environment id is the deliberate one: a server only ever
_is_ one environment, so the id in the path is compared rather than trusted.

## The browser pass (2026-09-07)

Run against `0de4c56c4` with a real headless Chromium driven by Playwright from a
throwaway script in `/tmp`, on the worktree's own `.t3` home. The reference
extension was installed through a **settings entry** rather than a launch flag —
the dev runner has no pass-through for `--extension` — which incidentally
exercised the other of the two sources. **22 of 22 checks passed**, after the
defect below.

The in-app preview tools were tried first and could not be trusted; that is its
own note ([preview-tools-unreliable-2026-09-07.md](preview-tools-unreliable-2026-09-07.md)).

### The extension could not load in dev at all

`DEV_PROXIED_PATH_PREFIXES` (`packages/shared/src/devProxy.ts`) listed `/api`,
`/oauth`, `/.well-known` and `/ws`. It did not list the extension seam's two
routes, so in single-origin browser dev **Vite answered them itself**: the
stylesheet `<link>` got `index.html` with a 200, and the bundle's dynamic
`import()` — which Vite rewrites to `entry.js?import` — got a 404. The extension
never mounted.

Only dev is affected; a packaged server serves both routes directly, which is why
the headless probe above passed against the server port and why nothing in the
test suites caught it. Fixed by adding `/ext-api` and `/ext-assets` to that one
list, which both the Vite proxy map and the server's dev catch-all read.

That the seam's own end-to-end evidence was collected against the server port,
bypassing the proxy the browser actually uses, is the reason this survived: the
probe and the browser do not take the same path to the same bytes.

### What the browser confirmed

| Check                                        | Result                                                                       |
| -------------------------------------------- | ---------------------------------------------------------------------------- |
| Sidebar entry for the extension              | present and labelled from the manifest                                       |
| Clicking it routes to `/ext/<env>/reference` | yes                                                                          |
| The bundle mounts in the host container      | `.t3ref-root` renders inside `div[data-extension='reference']`               |
| Stylesheet linked into the host document     | one `<link data-extension='reference'>`                                      |
| `hostApi.fetch` reaches the extension        | the status grid shows this environment's id                                  |
| Stylesheet scoping                           | 13 rules, **zero** outside `.t3ref-`                                         |
| Host theme                                   | the extension paints `rgb(38, 38, 38)`, resolved from the host's variables   |
| Navigating away                              | root removed **and** the `<link>` removed                                    |
| Settings row                                 | `reference 1.0.0 · Running · Settings entry · <path> · Tools reference_echo` |
| Disable → confirm                            | row flips to `Disabled`                                                      |
| Enable                                       | row returns to `Running`                                                     |
| A rebuild that changes bytes                 | `New build on disk` appears with no user action, and Deploy with it          |
| Deploy → confirm                             | back to `Running`, badge cleared                                             |
| Console                                      | no errors at any point                                                       |

**A no-op rebuild correctly does nothing.** The extension's build is
deterministic, so re-running it with unchanged sources produces byte-identical
output, the folder hash does not move, and no Deploy prompt appears. The first
attempt at this check failed for exactly that reason — the test was wrong, not
the product, and the behaviour is the one you want. The check now edits a source
file before building, and restores it afterwards.
